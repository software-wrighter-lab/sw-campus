4. Use SVG as your first 2.5D renderer

This is probably the most important implementation recommendation.

For the first version I would use:

Yew → SVG → browser DOM

not WebGL and not Three.js.

You can generate SVG directly from Yew's html! macro. Yew already works naturally with browser DOM APIs through WASM and web-sys; you don't need a JavaScript rendering layer.

An isometric building is just polygons:

          +--------+
         /        /|
        /  roof  / |
       +--------+  |
       |        |  |
       | front  | /
       |        |/
       +--------+

With the standard isometric projection:

screen_x = (world_x - world_y) * tile_width / 2
screen_y = (world_x + world_y) * tile_height / 2 - world_z

So in Rust you can have:

struct WorldPoint {
    x: f32,
    y: f32,
    z: f32,
}

struct ScreenPoint {
    x: f32,
    y: f32,
}

and:

fn project(point: WorldPoint) -> ScreenPoint

Everything else can remain normal SVG.

Advantages

SVG gives you:

native mouse hit testing;
hover;
click;
focus;
keyboard accessibility;
text labels;
CSS;
transforms;
animation;
responsive scaling;
browser tooltips;
straightforward Yew events;
no JS rendering library;
very small conceptual surface area.

And a building can literally be a link.

html! {
    <g onclick={onclick}>
        <polygon points={roof} />
        <polygon points={front} />
        <polygon points={side} />
        <text>{ "Computer History Museum" }</text>
    </g>
}

For a map containing perhaps tens or hundreds of objects, SVG performance should be entirely adequate.

If someday you have 10,000 animated objects, reconsider WebGL.

You're nowhere near needing that here.

5. Keep the world model separate from rendering

This will save you a lot of trouble later.

I would define something resembling:

pub struct Place {
    pub id: PlaceId,
    pub title: &'static str,
    pub kind: PlaceKind,
    pub summary: &'static str,
    pub parent: Option<PlaceId>,
    pub scene: Option<SceneId>,
    pub target: Target,
}

with:

pub enum PlaceKind {
    Campus,
    Building,
    Wing,
    Department,
    Exhibit,
    Project,
    Demo,
}

and:

pub enum Target {
    Scene(SceneId),
    InternalPage(PageId),
    ExternalUrl(&'static str),
}

Then geometry is separate:

pub struct SceneObject {
    pub place: PlaceId,
    pub position: GridPosition,
    pub footprint: Footprint,
    pub appearance: Appearance,
}

This distinction is important.

Semantic model

    parent = Computer History Museum
    kind   = Wing
Scene model
IBM 1130
    x = 7
    y = 4
    width = 4
    depth = 3

The IBM 1130 should not know where it is drawn.

That lets you redesign the maps without changing the information architecture.

6. Make routes correspond to semantic places

You specifically want links to every granularity.

I'd strongly support that.

Something like:

and:

/campus/computer-science/cor24/sw-tos

But internally I would not make the hierarchy dependent upon parsing those strings.

Instead:

#[derive(Clone, Routable, PartialEq)]
enum Route {
    #[at("/")]
    Home,

    #[at("/campus")]
    Campus,

    #[at("/campus/:building")]
    Building {
        building: String,
    },

    #[at("/campus/:building/:wing")]
    Wing {
        building: String,
        wing: String,
    },

    #[at("/campus/:building/:wing/:exhibit")]
    Exhibit {
        building: String,
        wing: String,
        exhibit: String,
    },

    #[not_found]
    #[at("/404")]
    NotFound,
}

yew-router supports dynamic path segments and nested routing patterns, so this maps naturally onto the application.

That also means navigation remains ordinary browser navigation:

Back works.
Forward works.
Open in new tab works.
Bookmarking works.
Sending URLs works.

Exactly what you want.

7. There is one important GitHub Pages wrinkle

Because you're likely to host these with GitHub Pages, you'll have to decide how direct deep links work.

Yew Router provides both BrowserRouter and HashRouter; BrowserRouter uses normal browser-history URLs, while HashRouter uses hash history.

For completely trouble-free static hosting you could use:

https://example.org/#/campus/computer-history/ibm-1130

That's ugly but reliable.

I personally think your project deserves nicer URLs:

https://projects.example.org/campus/computer-history/ibm-1130

So I'd use BrowserRouter and configure hosting so unknown paths return your WASM app's index.html.

If GitHub Pages remains the target, a small 404 SPA redirect scheme can accomplish this; if you later put the custom domain behind a static host with rewrite support, it becomes even cleaner.

I would therefore design around clean URLs from day one, even if the first deployment temporarily uses hashes.
